## 대화

### PM(NLP) 팀원

리뷰했습니다. 검색 API 계약(`contracts/api/documents.md`)과 필드 이름, offset 계산(`offset + limit`), 구절을 걸러 낸 뒤의 `hasMore` 처리가 맞게 연결되어 있습니다. 의견 남깁니다.

**1. (주요) "이 문서에서 찾기"에서 결과가 있는데도 없다고 나올 수 있습니다**
- 지금은 사업 전체에서 상위 50개를 받아 이 문서의 구절만 거릅니다. 문서가 많은 사업에서 이 문서의 관련 구절이 51위 밖에 있으면 "이 문서에서 찾은 구절이 없어요"가 뜹니다. 문서 모드에서는 `hasMore`가 항상 false라 더 불러올 방법도 없습니다.
- NLP `/v1/search`는 이미 `allowed_doc_ids`로 순위를 매기기 전에 문서를 거릅니다(`nlp/app/engine.py` `search`). 그래서 API 요청에 선택 필드 `documentId`를 추가하고, 백엔드에서 허용 목록을 그 문서 하나로 좁히기만 하면 해결됩니다. 백엔드 쪽 작업이 작아서 같이 하거나 바로 다음 PR로 하는 걸 제안합니다.
- 그 전까지는 빈 결과 문구를 "상위 결과에 이 문서의 구절이 없어요"처럼 바꿔서, 문서에 내용이 없는 것처럼 보이지 않게 하면 좋겠습니다.

**2. `useDocumentSearch.ts` loadMore의 offset**
- `nextOffset: latest.nextOffset + PASSAGE_LIMIT`는 `+ limit`이어야 합니다. 지금은 문서 모드에서 loadMore가 불리지 않아 문제가 드러나지 않지만, 문서 모드에서 더 보기를 켜면 offset이 어긋납니다.

**3. `MIN_PASSAGE_SCORE = 0.5`**
- 비교하는 점수는 원점수가 아니고 NLP가 소수 넷째 자리로 반올림한 값입니다(`engine.py` `round(float(cos[j]), 4)`). 그래서 0.49995~0.49999가 0.5로 통과합니다. 영향은 거의 없지만 참고로 적습니다.
- 이 기준은 임베딩 모델에 따라 달라집니다. 모델을 바꾸면 다시 재야 하니, 상수 옆 주석에 "측정한 모델과 근거(무의미한 검색어 최대 0.46, 관련 검색어 첫 결과 0.55 이상)"를 남겨 두면 좋겠습니다.

**4. 사소한 것**
- 디바운스(400ms) 중에도 `isLoading`이 true라, 한 글자 칠 때마다 스켈레톤이 바로 깜빡입니다. 의도한 거라면 괜찮습니다.

lint와 타입 검사는 PR 설명의 결과를 기준으로 봤고, 제가 직접 실행하지는 않았습니다.
