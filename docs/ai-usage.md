# AI 활용

화면 설계와 구현은 기준을 정해 직접 했고, **Claude Code**는 반복되는 일을 맡겼습니다. 공통 코드 정리, 해야 할 일 관리, 백엔드 PR 기록 정리와 누락 검증, 테스트입니다. 결과는 코드와 실제 화면으로 직접 확인했습니다.

| 맡긴 일 | 하는 일 |
| --- | --- |
| 공통 코드 정리 | 화면마다 복사된 오류 처리와 빈 화면 코드를 찾아 공용 컴포넌트와 훅으로 정리 |
| 해야 할 일 관리 | 매번 해야 할 일과 순서를 규칙으로 저장해 두고 작업마다 따르게 함 |
| 백엔드 PR 기록과 누락 검증 | 백엔드 PR의 계약서와 코드를 읽고 영역별로 정리해 저장한 뒤, 화면에서 빠뜨린 것이 없는지 대조 |
| 테스트 | 손으로 하기 어려운 상황을 스크립트로 재현하고 결과를 기록 |

## 쓰는 방식

AI에게 일을 맡기기 전에 **읽을 자료와 순서를 규칙으로 정해 저장**해 두었습니다. 규칙은 Claude Code의 메모리 파일로 저장해서 매 작업마다 자동으로 불러오게 했고, 새 API를 붙일 때마다 쌓은 백엔드 정리 노트(`api-정리/`)를 먼저 읽게 했습니다.

실제 예시입니다. 템플릿 마감 계산에서 규칙 실수 두 개가 리뷰로 발견된 날, 이렇게 규칙을 정했습니다.

<table>
  <tr>
    <td width="20%" align="right"><b>작성 요청(요약 ver)</b></td>
    <td>관련된 api 문서가 포함된 pr의 코드는 다 읽어보고 나서 기록해두는 게 좋을 것 같아. 관련 기록 중복으로 이미 기록해뒀는지 확인한 다음에 없다면 정리해 줘.</td>
  </tr>
  <tr>
    <td align="right"><b>Claude Code</b></td>
    <td>백엔드 PR의 문서랑 코드를 불러올게. 먼저 로컬에 읽고 정리해둔 게 있는지 확인할게.</td>
  </tr>
  <tr>
    <td align="right"><b>저장되는 것</b></td>
    <td>그 API를 바꾼 백엔드 PR을 모두 찾아 계약서, 컨트롤러, 요청·응답 형식, 서비스 코드를 읽고, 출처 PR, 엔드포인트, 검증 규칙과 실제 동작의 차이, 오류, 경계 사례, 미구현을 <code>api-정리/서비스토큰.md</code>처럼 영역별 파일로 저장</td>
  </tr>
  <tr>
    <td align="right"><b>이후 작업</b></td>
    <td>저장된 정리와 화면 코드를 대조해 빠진 요청, 응답, 오류 처리가 없는지 점검하고, 실제 서버로 동작을 확인한 결과를 보고</td>
  </tr>
</table>

이 규칙은 이후 서비스 토큰, 설정 내보내기와 가져오기, 물어보기 관리 화면을 연결할 때마다 같은 순서로 적용됐고, 영역마다 정리 파일이 쌓였습니다.

## 잘된 사례

| 작업 | AI 지원 | 확인 방법 |
| --- | --- | --- |
| 오류와 빈 화면 공용화 | 화면 26곳의 기본 결과 화면과 30곳에 복사된 오류 처리 코드를 찾아 공용 컴포넌트와 훅으로 정리 | 바꾸기 전후 56개 화면을 PC와 모바일로 열어 결과가 같은지 비교 ([PR 150](pull-requests/150.md)) |
| API 연결 전 계약 정리 | 새 API를 붙이기 전 관련 백엔드 PR의 계약서와 코드를 읽고 요청, 응답, 오류, 경계 사례를 정리 | 정리한 내용과 화면 코드를 대조한 뒤 실제 서버에서 화면 동작 확인 |
| 손으로 하기 어려운 화면 테스트 | 버튼 연타, 두 탭에서 같은 데이터 수정, 서버 오류 상황을 스크립트로 재현 | 테스트 케이스 54건의 결과를 직접 대조해 [테스트 케이스](qa.md)에 기록 |
